# 해달 낚시 · 해먹 · 창고 설계

- 상태: 1차 구현 + 홈 광고 부스트 (토스 포인트 전환·해먹 가득 푸시는 후속 작업)
- 작성일: 2026-11-02
- 관련 ADR: [ADR-0007 낚시 경제](../adr/0007-fishing-economy.md), [ADR-0003 재화 이름](../adr/0003-in-app-currency-name.md)
- 데이터 시퀀스: [fishing-sequence.md](./fishing-sequence.md)

## 1. 개요

해달이 시간에 따라 물고기를 잡아 **해먹**에 쌓는다. 해먹은 용량이 있어 가득 차면 더 잡지 않는다.
사용자가 해먹의 물고기를 **창고**로 옮겨야 영속 재화가 된다.
퀴즈(광고 시청)와 출석은 물고기 대신 **낚시 속도**를 올린다.

### 범위

| 포함 (1차) | 제외 (후속 작업) |
|---|---|
| 시간 기반 낚시 (앱을 꺼도 쌓임, 해먹 용량에서 멈춤) | 창고 → 토스 포인트 전환 (프로모션 API) |
| 해먹 → 창고 저장과 창고 원장 | 해먹 가득 푸시 (알림 동의문, 문구 검수, 08시 지연) |
| 퀴즈 광고 보상 → 낚싯대 강화 +10% | 해달 2마리 캔버스 연출 |
| 출석 1~6일차 → 낚싯대 강화 +10%, 7일차 → 해달 친구 | |
| 출석 '광고 보고 2배' → 같은 보상 한 번 더 (7일차는 해달 친구 한 명 더) | |
| 홈 '광고 보고 낚싯대 강화' (20분 쿨타임), '광고 보고 해먹 넓히기' (5단계, 1시간 쿨타임) | |
| 홈 화면 낚시 현황과 저장 버튼 | |

## 2. 정책값

모든 수치는 `apps/api/src/common/globals/fishing.policy.ts`에 있다. 값만 바꾸면 되고, DB·로직은 그대로다.

| 상수 | 값 | 의미 |
|---|---|---|
| `FISH_PER_TOSS_POINT` | 500 | 물고기 500마리 = 토스 포인트 1원 (확정) |
| `BASE_MONTHLY_TOSS_POINTS` / `BASE_MONTH_DAYS` | 1000 / 30 | 강화 0단계로 30일 낚시하면 1,000원 → 기본 속도 시간당 약 694.4마리 |
| `HAMMOCK_CAPACITY` | 5,000 (임시) | 해먹 용량 (마리) |
| `MONTHLY_TOSS_POINT_BUDGET` | 5,000 | 사용자 1명 월 예산. 코드로 강제하지 않고 테스트로 지킨다 |
| `ROD_POLICY.SPEED_BONUS_PERCENT_PER_LEVEL` | 10 | 강화 1단계 = 기본 속도의 +10% |
| `ROD_POLICY.MAX_LEVEL` | 10 (임시) | 하루 최대 강화 단계 |

| `OTTER_FRIEND_POLICY.CAPACITY_BONUS_PERCENT` | 50 | 해달 친구 한 명당 해먹 용량 +50% |
| `OTTER_FRIEND_POLICY.MAX_PER_DAY` | 2 | 하루 해달 친구 최대 인원 (7일차 출석 1 + 출석 광고 2배 1) |
| `QUIZ_POLICY.ROD_LEVELS_PER_REWARD` | 1 | 퀴즈 광고 1회당 강화 단계 |

| `HAMMOCK_EXPAND_POLICY.CAPACITY_BONUS_PERCENT_PER_LEVEL` | 10 | 해먹 1단계당 용량 +10% (복리 아님) |
| `HAMMOCK_EXPAND_POLICY.MAX_LEVEL` | 5 | 하루 최대 해먹 단계 (+50%) |
| `HAMMOCK_EXPAND_POLICY.LEVELS_PER_AD` | 1 | 광고 1회당 해먹 단계 |
| `HAMMOCK_EXPAND_POLICY.COOLDOWN_MINUTES` | 60 | 홈 광고 해먹 넓히기 쿨타임 (분) |

출석 일차별 보상은 `modules/attendance/lib/attendance-reward.policy.ts`에 있다 (1~6일차 강화 +1단계, 7일차 해달 친구).

### 계산식

```
속도(%)   = 100 + 10 × 강화 단계 + 100 × 해달 친구 수
해먹 용량 = 5,000 × (100 + 50 × 해달 친구 수 + 10 × 해먹 단계) / 100
```

강화 단계는 퀴즈·출석·홈 광고 어디서 올리든 하루 `MAX_LEVEL`(10)에서 멈춘다.
해먹 단계는 홈 광고로만 오르며, 정해진 순서로 한 단계씩 넓어진다 (그물 → 나무 → 대나무 → 산호 → 진주 해먹).
**랜덤으로 뽑지 않는다.** 물고기는 토스 포인트로 바뀌는 자체 포인트라, 용량이 운에 따라 달라지면 프로모션의 "고정 지급만 허용" 원칙과
비게임 분류(확률형 요소 → 게임물 분류 위험, 익명 식별키는 비게임 전용)에 걸릴 수 있다 (2026-11-03 문서 확인).
홈 광고 강화가 없으면 하루 최대 4단계(퀴즈 3 + 출석 1)라 최대 단계까지 채울 수 없었다.

### 예산 안전장치

`modules/fishing/__test__/fishing-budget.spec.ts`가 최악의 한 달을 계산한다.

- 31일 내내 최대 강화, 해달 친구가 올 수 있는 최대 일수(⌈31 ÷ 7⌉ = 5일, 그날은 최대 2명), 해먹을 한 번도 넘치지 않게 비움
- 임시값 기준 (31 × 200% + 5 × 200%) × 33.3원 ≈ **2,400원** ≤ 5,000원
- 해먹 넓히기는 속도를 바꾸지 않아 이 최악값에 영향이 없다. 자주 들어오지 않는 사용자가 덜 놓치게 할 뿐이다.
- 정책값을 바꿔 5,000원을 넘으면 테스트가 실패해 배포 전에 걸린다.

## 3. 상태와 계산

### 저장하는 상태 (`fishing_states`, 사용자당 한 행)

| 컬럼 | 의미 |
|---|---|
| `hammock_milli_fish` | 해먹의 물고기 (1/1000마리 단위 정수). 소수점을 버리지 않고 이어서 센다 |
| `settled_at` | 마지막으로 해먹을 정산한 시각 |
| `rod_level`, `rod_level_date` | 강화 단계와 그 단계가 유효한 날짜 (KST). 날짜가 오늘이 아니면 0단계 |
| `otter_friend_date`, `otter_friend_count` | 해달 친구가 오는 날짜 (KST)와 인원. 날짜가 오늘이 아니면 0명 |
| `hammock_level`, `hammock_level_date` | 광고로 넓힌 해먹 단계와 그 단계가 유효한 날짜 (KST). 날짜가 오늘이 아니면 0단계 |
| `ad_hammock_expanded_at` | 마지막 홈 광고 해먹 넓히기 시각. 이 시각 + 1시간이 지나야 다시 넓힐 수 있다 |
| `ad_rod_enhanced_at` | 마지막 홈 광고 강화 시각. 이 시각 + 20분이 지나야 다시 강화할 수 있다 |
| `warehouse_fish` | 창고 잔액 |

자정 초기화를 배치로 처리하지 않는다. "유효 날짜가 오늘인가"로 판단한다.
사용자는 처음 홈 화면을 열 때 행이 만들어지고, 그때부터 낚시가 시작된다.

### 정산 (`lib/settle-hammock.ts`)

속도가 바뀌는 때는 두 가지뿐이다.

1. **사용자 행동** (강화, 해달 친구, 해먹 넓히기): 바꾸기 직전에 정산한다. 그래서 정산 시점 사이에는 속도·용량이 일정하다.
2. **KST 자정**: 강화·해달 친구·해먹 넓히기가 풀린다. 자정 이후는 행동이 없는 한 기본 속도·기본 용량이다.

따라서 정산은 최대 두 구간이다.

```
settled_at ──[그날 속도·용량]── 다음 자정 ──[기본 속도·기본 용량]── now
```

- 각 구간에서 `min(용량, 보유량 + 속도 × 시간)`으로 쌓는다.
- 보유량이 이미 용량 이상이면 그 구간에서는 더 쌓지 않는다. 해달 친구가 끝나 용량이 줄어도 **이미 잡은 물고기는 줄이지 않는다.**
- `GET /fishing/me`는 저장하지 않고 계산만 한다. 저장·강화·해달 친구만 정산 결과를 DB에 쓴다.

### 가득 차는 시각 (`predictHammockFullAt`)

정산 직후 상태에서 같은 두 구간으로 계산한다. 이미 가득이면 `null`.
해먹 가득 푸시(후속 작업)도 이 함수를 쓴다.

## 4. API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/fishing/me` | 해먹 수량·용량·가득 차는 시각, 속도, 강화 단계, 해달 친구 여부, 창고 잔액 |
| POST | `/api/fishing/store` | 해먹의 물고기(정수 부분)를 창고로 옮기고 원장에 기록. 1마리 미만이면 409 |
| POST | `/api/fishing/ad-enhance-rod` | 광고 시청 후 오늘 강화 +1단계. 쿨타임 안이거나 오늘 최대 단계면 409. 응답은 바뀐 뒤의 현황 |
| POST | `/api/fishing/ad-expand-hammock` | 광고 시청 후 오늘 해먹 +1단계(용량 +10%). 쿨타임 안이거나 오늘 최대 단계면 409. 응답은 바뀐 뒤의 현황 |

두 광고 API는 웹이 보상형 광고의 `userEarnedReward`를 받은 뒤에만 부른다. 서버는 광고 시청을 직접 확인할 수 없으므로
쿨타임과 최대 단계가 서버 쪽 한도다. 현황 응답의 `adRodEnhanceAvailableAt`, `adHammockExpandAvailableAt`(쿨타임이 끝나는 시각,
지금 가능하면 null)으로 웹이 버튼을 막고 남은 시간을 보여준다.

다른 모듈이 쓰는 `FishingService` 메서드 (호출하는 쪽의 트랜잭션 안에서 실행):

- `enhanceRod(userId, levels, manager)`: 정산 → 오늘 강화 단계 + levels (최대 단계에서 멈춤)
- `summonOtterFriend(userId, manager)`: 정산 → 오늘 해달 친구 한 명 더 (하루 최대 2명)

### 동시성

해먹이 바뀌는 작업은 모두 트랜잭션 안에서 `fishing_states` 행을 `SELECT … FOR UPDATE`로 잠근다.
퀴즈 보상 기록 + 강화, 출석 기록 + 강화(또는 해달 친구)는 **같은 트랜잭션**이다.
그래서 퀴즈 보상은 기록됐는데 강화가 안 되는 일이 없다.

## 6. 화면

- 홈: 해먹 게이지(N / 용량), **광고 보고 창고에 저장하기** 버튼 (광고를 쓸 수 없거나 불러오지 못하면 광고 없이 **창고에 저장하기**. 저장 중에는 스피너. 남은 시간·창고 수량·낚시 속도 표시는 2026-11-02 화면에서 제외. API 응답에는 남아 있다)
- 홈: **광고 보고 낚싯대 강화하기 (+10%)**, **광고 보고 (다음 단계) 해먹으로 넓히기 (+10%)** 버튼과 "오늘 자정까지 유지돼요" 안내. 해먹 게이지 제목에 지금 해먹 이름을 보여준다. 쿨타임 중에는 "N분(N시간 M분) 뒤에 다시 …할 수 있어요", 최대 단계면 막힌 버튼으로 바꾸고 광고를 띄우지 않는다
- 홈의 보상형 광고 버튼(창고 저장·출석 2배 포함)은 광고 하나를 함께 쓴다. 같은 광고 그룹은 한 번에 하나만 미리 불러올 수 있다
- 해먹 수량은 응답을 받은 시각부터 속도로 화면에서만 늘려 보여준다 (`entities/fishing/lib/project-hammock.ts`). 실제 수량은 서버 값이다.
- 60초마다 다시 조회한다. 자정(`boostsResetAt`) 이후는 속도가 바뀌므로 화면에서 늘리지 않고 다음 조회 값으로 맞춘다 (적게 보일 수는 있어도 많게 보이지 않는다).

## 7. 배포 순서

이전 코드는 `quiz_attempts.reward_amount`를 조회하고, 새 코드는 `fishing_states`가 있어야 출석·퀴즈 보상이 동작한다.
그래서 한 번에 처리하지 않는다.

1. 마이그레이션 `CreateFishing` 실행 (새 테이블만 추가 → 이전 코드에 영향 없음)
   - 광고 부스트: `FishingAdBoosts` (컬럼 추가만, 기본값이 있어 이전 코드에 영향 없음). 이미 해달 친구가 온 행은 인원 1로 채운다
2. api와 web을 **함께** 배포 (응답 타입이 바뀌어 이전 web 번들은 퀴즈 보상 문구가 깨진다)
3. 배포가 끝난 뒤 `quiz_attempts.reward_amount` 컬럼 삭제 마이그레이션을 별도 PR로 추가·실행 (nullable 이라 남아 있어도 새 코드는 문제없다)

## 8. 운영 시 주의

- 속도 관련 정책값(`BASE_MONTHLY_TOSS_POINTS`, 보너스 %)을 바꿔 배포하면, 각 사용자의 마지막 정산 이후 시간도 새 속도로 계산된다.
  해먹 용량 이상은 쌓이지 않으므로 영향은 사용자당 해먹 1회분 이내다.
- 강화·해달 친구 날짜는 보상을 기록한 요청 시각 하나로 정한다. 자정 직전 출석·퀴즈 보상이 다음 날로 넘어가지 않는다.

## 9. 후속 작업: 해먹 가득 푸시

앱인토스 정책(2026-11-02 확인):

- 기능성 메시지로만 보낼 수 있다. "저장하러 오세요" 같은 재방문 유도 문구는 쓸 수 없다.
- 조건형 알림이므로 알림 동의문 등록과 `requestNotificationAgreement`로 동의를 받아야 할 가능성이 높다.
- 문구 검수 승인 전에는 테스트 발송도 안 된다. 발송 코드는 `{appName}-`(현재 `headaltest-`)으로 시작해야 한다.
- 단건 발송(`send-message`)은 야간에도 나가지만, **야간(21~08시)에 가득 차면 08시로 미룬다** (결정 사항).
- 구현 방향: 정산할 때 `predictHammockFullAt`으로 가득 찰 시각을 저장하고, 주기 작업이 시각이 지난 사용자에게 한 번만 보낸다.
