# ADR-0006: 서버는 일회용 코드 교환으로 사용자를 확인하고 자체 토큰을 발급한다

- 상태: Proposed (팀 논의 후 확정 예정)
- 날짜: 2026-11-02
- 대체 대상: ADR-0004 (이 ADR이 Accepted 되면 ADR-0004를 `Superseded by ADR-0006`으로 바꾼다)

## 맥락 (Context)

해달해달 서버는 사용자별 물고기 잔액과 참여 이력을 관리하고, 프로모션 API로 토스 포인트를 지급한다.
따라서 "이 요청을 보낸 사람이 누구인가"를 서버가 확실히 알아야 한다.
식별이 뚫리면 남의 물고기를 전환해 가는 금전 사고로 이어진다.

ADR-0004는 클라이언트가 `getAnonymousKey()`로 받은 hash를 서버로 보내고,
서버가 식별키 검증 API로 확인하기로 했다. 그러나 앱인토스 문서는 이 방식이
사용자 인증으로 충분하지 않다고 밝힌다.

- 식별키 검증 API는 "이 미니앱에서 발급된 키인지만 확인하고, 요청을 보낸 쪽이
  그 사용자임을 증명하지는 않는다."
- "미니앱에서 사용자 식별키를 직접 파트너 서버로 전달하면, 식별키가 노출됐을 때
  제3자가 같은 사용자처럼 요청할 수 있다."

이 문제는 식별자의 종류(익명키, 토스 로그인 userKey)와 상관없이,
클라이언트가 보낸 식별자를 서버가 믿는 구조 자체에서 생긴다.

현재 코드도 같은 문제를 갖고 있다.

- 임시 식별: 클라이언트가 보낸 `X-User-Id` 헤더를 그대로 믿는다.
- `users` 테이블: 익명키 방식으로는 받을 수 없는 `email`과 `name`이 필수다.

## 결정 (Decision)

### 원칙 (식별 방식과 무관하게 유지)

1. 서버는 클라이언트가 보낸 사용자 식별자(hash, userKey, userId 등)를 믿지 않는다.
2. 클라이언트는 SDK가 발급한 **일회용 코드**만 서버로 보낸다.
   서버는 이 코드를 mTLS로 앱인토스 파트너 API에 교환해 식별자를 얻는다.
3. 서버는 얻은 식별자로 회원을 찾거나 만들고, 내부 사용자 ID(uuid)에 연결한다.
   다른 모듈은 내부 uuid만 참조하고, 토스 식별자를 직접 알지 않는다.
4. 서버는 **자체 access token**을 발급한다. 이후 모든 API는
   `Authorization: Bearer <token>`에서 내부 사용자 ID를 꺼낸다.
   WebView에서 API 서버가 다른 도메인일 때 쿠키가 막힐 수 있으므로 쿠키는 쓰지 않는다.
5. 앱인토스 API(프로모션 등)에 보내는 식별자는 서버 DB에 저장된 값만 쓴다.
   토스 식별자는 클라이언트 응답에 내보내지 않는다.

### 식별자 출처 (현재 결정)

**익명키**를 사용한다. 로그인 화면이나 약관 동의 없이 식별하고, 회원 정보(이름·이메일 등)는 받지 않는다.

1. 클라이언트: 진입 시 `User.createAnonymousKeyAuthCode()`로 코드를 받는다.
   코드는 300초 동안 한 번만 쓸 수 있으므로 저장하지 않고 즉시 `POST /api/auth/anon`으로 보낸다.
2. 서버: `POST /api-partner/v1/apps-in-toss/users/anon-key/exchange`로 코드를 교환해 `anonKey`를 얻는다.
   `resultType`이 `SUCCESS`가 아니면 모두 실패로 처리한다.
3. 서버: `users.anon_key`로 회원을 찾거나 만들고 토큰을 발급한다.
4. 토큰이 만료돼 401이 오면 클라이언트가 1번부터 다시 진행한다.
   로그인 화면이 없으므로 사용자에게는 보이지 않는다.
5. 프로모션 API는 `x-anon-key`에 DB의 `anon_key`를 넣어 호출한다.

### 대안: 토스 로그인

`appLogin()`으로 인가 코드를 받고, 서버가 토큰 발급과 사용자 정보 API를 거쳐 `userKey`를 얻는 방식이다.
위 원칙 2~5를 그대로 만족하므로 바꾸게 되더라도 원칙과 코드 구조는 유지되고,
'식별자 출처'만 새 ADR로 대체한다.

현재 채택하지 않은 이유:

- 해달해달에는 이름·연락처 같은 회원 정보가 필요 없다.
- 첫 진입 시 약관 동의 화면이 생겨 이탈이 늘 수 있다.
- 추가 부담이 생긴다: 콘솔 약관 설정, 인트로 화면에 서비스 설명 제공,
  사용자가 로그인 연결을 끊으면 그 사용자 데이터를 삭제해야 함, 개인정보 복호화.

## 결과 (Consequences)

긍정

- 토스 식별자가 노출돼도 그것만으로는 다른 사용자처럼 요청할 수 없다.
- 식별 방식을 바꿔도 출석체크 등 내부 uuid를 쓰는 모듈은 영향을 받지 않는다.
- 사용자는 로그인 화면 없이 바로 앱을 쓴다.

부정 / 비용

- 서버에 mTLS 인증서가 필요하다. 콘솔의 개발 > mTLS 인증서에서 발급하고,
  개인 키는 저장소에 올리지 않고 환경 변수나 시크릿으로 관리한다.
  만료 전에 재발급해서 교체해야 한다.
- 로컬 개발 환경에서는 devtools mock이 가짜 코드를 주므로 실제 교환 API를 호출할 수 없다.
  `NODE_ENV=development`에서만 켜지는 개발용 교환 경로가 필요하다.
  이 경로는 production에서 켜지면 안 되며, 서버 시작 시 이를 검사해 켜져 있으면 기동을 실패시킨다.
- 교환 API는 앱당 분당 3,000회 제한이 있다. 진입할 때와 토큰 만료 시에만 교환한다.

후속 작업

- 마이그레이션: `users`에서 `email`과 `name`을 제거하고 `anon_key`(NOT NULL, UNIQUE)를 추가한다.
  2026-11-02 기준 DB에 테이블이 없으므로 기존 마이그레이션을 고쳐도 된다.
- `auth` 모듈 신설: 코드 교환, 토큰 발급과 검증, `CurrentUserId` 데코레이터 구현 교체.
- 임시 식별 제거: `X-User-Id` 헤더, 웹의 `dev-user-id`와 userId 입력란,
  사용자 생성 폼, 인증 없이 열린 `GET/POST /api/users`.
- 웹: 진입 시 인증하는 흐름과 401 재인증을 `http-client`에 넣는다.
- 확정 시: ADR-0004의 상태를 `Superseded by ADR-0006`으로 바꾸고, CLAUDE.md의 '사용자 식별 방식'을 갱신한다.

미결정 (팀 논의)

- 토큰 형식: 서명된 JWT(서버 저장 없음, 단순) 또는 DB 세션 테이블(강제 만료 가능).
- 토큰 유효기간.
- 익명키로 프로모션을 서버에서 지급할 수 있는지:
  ADR-0004 작성 당시 프로모션 가이드의 "서버 지급 시 토스 로그인 필요" 문구와 상충한다고 기록했다.
  현재 토스 로그인 소개 문서에는 "프로모션 포인트 지급 … 토스 로그인뿐 아니라
  사용자 식별키(anonKey)로도 사용할 수 있어요"라고 명시돼 있다.
  최종 확인은 앱인토스 문의 답변으로 하며, 토스 로그인이 필요하다고 답변받으면
  '식별자 출처'만 새 ADR로 대체한다.
